# Журнал решений

Формат: вопрос → варианты → выбор и статус → почему → чем проверено → что потеряли → что изменило бы решение.
Статусы: **реализовано**, **отложено**, **отвергнуто**. Цифры — только из `docs/EXPERIMENTS.md` (этот код, эта машина).

Дефолты из раздела 5 handoff пользователь отдельно не подтверждал: в постановке было «начни реализацию», поэтому D1–D8 приняты как рекомендованные в handoff и помечены так явно.

---

## D1. Подтверждающий движок — стандартный `regexp`, без переписывания паттернов
- **Варианты:** `regexp` как есть; `regexp` + Latin-1 адаптер и переписывание `$`; `regexp2` для несовместимых; Hyperscan через cgo.
- **Выбор:** `regexp`, исходник паттерна передаётся без изменений, добавляются только флаги `(?i)`/`(?s)`. **Реализовано** (`probes.go`).
- **Почему:** handoff §9 — не вводить одновременно fallback, PCRE-переписчик и второй движок. Naive и fast обязаны иметь одну семантику, иначе diff ничего не значит.
- **Проверено:** E1 — 11 365 из 12 172 компилируются, 807 (6.6%) нет; отчёт по причинам печатается при каждом запуске.
- **Что потеряли:** 807 паттернов не участвуют совсем. Остальные компилируются, но значат не то же, что в PCRE: `.` и классы считают руны, `\xff` — это U+00FF (байты `C3 BF`), `$` — только конец текста, `(?i)` сворачивает по Unicode. Это зафиксировано тестами (`TestExpectations`), а не исправлено.
- **Изменило бы:** требование совпадать с PCRE побайтно → нужен байтовый движок, а не адаптер поверх рунового.

## D2. Несовместимые паттерны — явный учёт и исключение
- **Выбор:** не компилируется → в `Rules.Unsupported` с одной основной причиной; в выдаче не участвует. **Реализовано.**
- **Почему:** ТЗ допускает несовместимость. Молча терять нельзя, поэтому счёт и разбивка печатаются всегда.
- **Что потеряли:** неизвестное число совпадений. Утверждать, что эти 807 «не срабатывают», нельзя — это не измерялось.

## D3. Результат — полный список, `hard` и `soft` отдельно, без вердикта
- **Выбор:** `{"id":N,"hard":[...],"soft":[...]}` на каждый запрос, включая пустые. Внутри списка — порядок приоритета и дедуп по имени сервиса; сервис, попавший в оба списка, остаётся в обоих. **Реализовано** (`appendResult`, `TestResultLine`).
- **Почему:** «первый hard, иначе soft» — не семантика nmap (handoff §12). Полный список не требует раннего выхода и не теряет информацию.
- **Изменило бы:** явная спецификация редьюсера вердикта.

## D4. Приоритет — порядок Probe в файле, затем порядок строк
- **Выбор:** ID паттерна = его порядковый номер среди скомпилированных в порядке файла; кандидаты обходятся по возрастанию ID. **Реализовано.**
- **Почему:** воспроизводимо и не требует модели сканера. `rarity`, `ports`, `fallback` не используются: это параметры отправки probe, которой у нас нет.
- **Оговорка:** это наш порядок, не расписание nmap.

## D5. TCP и UDP — весь набор
- **Выбор:** все 188 probe. **Реализовано.** Исключение UDP уменьшило бы нагрузку из ТЗ.

## D6. Нормализация
- **Выбор:** `METHOD SP URL SP HTTP/1.1 CRLF`, заголовки `Имя: значение CRLF` в порядке и регистре JSON, пустая строка, тело целиком. JSON-escapes декодируются; percent-decoding, lowercase и обрезки тела нет. Версия нормализации — в `manifest.json`. **Реализовано** (`appendRequest`).
- **Почему:** любое из отвергнутых преобразований меняет байты и, значит, совпадения. Порядок заголовков берётся из потокового декодера, а не из `map`.
- **Что потеряли:** `HTTP/1.1` — выдуманная нами версия; в данных её нет. Бинарные тела, побывавшие в JSON, уже не исходные байты.

## D7. Бинарный корпус: `corpus.bin` + `corpus.idx` + `manifest.json`
- **Варианты:** всё в куче; конвейер reader→workers; run-to-completion по файлам; бинарник с индексом.
- **Выбор:** запросы подряд, индекс из N+1 смещений `uint64`, без length-prefix. Файлы публикуются переименованием после успеха. **Реализовано** (`Convert`, `OpenStore`).
- **Почему:** JSON уходит из matcher, запрос доступен по номеру, батч — это диапазон ID.
- **Проверено:** E1 (время конвертации), `TestStoreRejectsDamage` (усечённый bin, битый magic, лишнее/неупорядоченное смещение, чужая версия).
- **Отступление от handoff:** конвертер держит в памяти до `workers` декодированных файлов целиком, а не один объект. Пик RSS в E1 — 1.4 ГБ. Строго потоковая запись была бы однопоточной.
- **Что потеряли:** +5.4 ГБ на диске и отдельная фаза, время которой нельзя прятать.

## D8. Раздача работы — общий атомарный курсор, батч 256
- **Выбор:** `next.Add(batch)`, начало диапазона = результат − batch. Всё изменяемое — в `Worker`. **Реализовано** (`Run`).
- **Проверено:** `TestRunWorkersAndOutput` (короткий последний батч, батч больше корпуса), `check` (1 воркер против N). Хеш строки результата пишется через `atomic.Swap`, повторная обработка ID считается и обязана быть нулём.
- **Размер батча:** E10 — от 16 до 4096 разницы за пределами шума нет. 256 оставлено как значение по умолчанию, оптимумом оно не является.

## D9. Вывод — один файл, общий `bufio.Writer` под мьютексом на батч
- **Варианты:** файл на воркер; общий writer; отдельная горутина-писатель.
- **Выбор:** воркер форматирует батч в свой буфер и под мьютексом копирует его в writer. **Реализовано.**
- **Почему:** одна блокировка на 256 запросов; владение буфером не передаётся, он копируется до переиспользования.
- **Что потеряли:** порядок строк произвольный. Сравнение прогонов идёт по хешу строки для каждого ID, а не по файлу.
- **Оговорка:** время включает форматирование и `Flush`, но не `fsync`.

## D10. Предфильтр — необходимые условия из AST
- **Выбор:** `regexp/syntax` с теми же флагами, что у компиляции. **Реализовано** (`filter.go`). Для каждого паттерна — один класс:
  1. **префикс от начала текста** (10 941 паттерн): все совпадения начинаются в позиции 0 с одного из литералов; индекс по первым двум байтам;
  2. **обязательный литерал** (379): совпадение содержит хотя бы один из литералов; один проход по запросу;
  3. **always** (45): условие не доказано, паттерн проверяется всегда.
  Поверх класса — нижняя граница длины, а для `...$` — верхняя граница длины и множество допустимых последних байт; для заякоренных без префикса — множество первых байт.
- **Правила вывода:** Concat — годится требование любого потомка; Alternate — объединение по всем веткам, ветка без требования обнуляет всё; `?`, `*`, `{0,n}` ничего не требуют. Заякоренность считается по дереву: `^A|B` не заякорен.
- **Почему байтовые условия корректны для рунового движка:** Go декодирует вход как UTF-8, руна литерала совпадает только со своей канонической кодировкой. U+FFFD исключён (совпадает с любым невалидным байтом).
- **Проверено:** `TestFastEqualsNaive` (каждое правило набора хотя бы раз срабатывает), `TestExpectations`, `check` на реальных запросах.
- **Не доказано:** отсутствие ложных отрицаний для произвольного входа. Есть вывод по правилам и найденное отсутствие расхождений, формального доказательства нет.

## D11. Регистронезависимые литералы — только из «безопасных» байт
- **Проблема:** в E4 три паттерна `(?si)^.*<address>Apache/...` давали 204 из 229 мкс regex-времени на запрос: с `(?i)` литерал не извлекался.
- **Выбор:** под `(?i)` берутся максимальные отрезки из ASCII-рун, чья орбита свёртки не выходит за ASCII. Исключены `k` (U+212A) и `s` (U+017F). Сравнение — без учёта ASCII-регистра. **Реализовано** (`foldSafe`, `literalRuns`).
- **Проверено:** `TestFoldSafe` перебирает все ASCII-руны; `TestFoldConditions` — входы с `ſ` и `K` внутри литерала.
- **Эффект:** E5.

## D12. Поиск литералов — один проход с 3-граммным Bloom-фильтром
- **Варианты:** `bytes.Index` на каждый литерал; готовая библиотека Aho–Corasick; свой однопроходный фильтр.
- **Выбор:** свой фильтр: обе 3-граммы (смещения 0 и 1) каждого литерала длиной ≥4 в Bloom-фильтре на 16 КБ, проверяется каждая чётная позиция, попадание подтверждается сравнением. **Реализовано** (`scan`).
- **Почему:** E2 — 276 отдельных `bytes.Contains` занимали больше половины времени. Aho–Corasick в этом проекте не измерялся; выбор сделан в пользу ~60 строк без зависимостей.
- **Короткие литералы:** в E6 литералы из 2–3 обычных байт (`"19"`, `":0"`, `"\r\n"`) довели `IndexByte` до 88% профиля. Теперь короче 4 байт допускаются только начинающиеся с управляющего байта (NUL и подобные), таких 9.
- **Изменило бы:** профиль, где `scan` снова доминирует, — тогда сравнить с Aho–Corasick.

## D13. Эквивалентное подтверждение для `(?s)^.*X`
- **Выбор:** для 8 паттернов этого вида fast-путь подтверждает выражением `X` без якоря. Naive использует оригинал. **Реализовано** (`analyze`, `Filter.confirm`).
- **Почему:** с флагом `s` выражение `.*` принимает любой префикс, поэтому `^.*X` совпадает тогда и только тогда, когда `X` совпадает где-то. Go исполняет заякоренную форму общим автоматом, а для `X` перескакивает к литеральному префиксу. В E5 один такой паттерн стоил 11.6 из 20.4 мкс.
- **Чем отличается от запрещённого переписывания:** это замена Go-выражения на эквивалентное Go-выражение, а не перевод PCRE. Naive её не использует, поэтому diff её проверяет.

## D14. Доступ к запросам — mmap
- **Варианты:** mmap; `pread` диапазона батча в буфер воркера.
- **Выбор:** mmap по умолчанию; `-access pread` оставлен как флаг эксперимента. **Реализовано.**
- **Почему:** E8 — оба варианта дают одно время в пределах шума; `madvise` ничего не меняет. mmap проще и без копии.
- **Что это стоит:** страницы файла входят в RSS; корпус должен помещаться в page cache, иначе прогон упирается в диск.

## D15. Замеры — выборка baseline «каждый k-й запрос»
- **Выбор:** `-sample N` берёт запросы с шагом `Count/N` по всему корпусу. Naive и fast идут по одним и тем же ID. **Реализовано.**
- **Почему:** первые 100k — это несколько сайтов из начала алфавита; шаг по корпусу захватывает и legit, и malicious, и большие тела.
- **Оговорка:** выборка с шагом читает страницы вразброс, поэтому req/s fast-режима на выборке и на полном корпусе — разные числа; сравнивать их между собой нельзя.

## Отложено

| Что | Почему |
|---|---|
| Latin-1 адаптер, переписывание `$` | меняет семантику движка; требует своей спецификации и сверки с PCRE |
| `regexp2` для 807 паттернов | второй движок с .NET-семантикой и backtracking; отдельный эксперимент |
| Сверка с эталоном PCRE | не делалась; совместимость с PCRE не заявляется |
| Checkpoint, watermark, шарды | сценарий 100M/1B, описан в README |
| Сортировка батчей по байтам | E10 не показал проблемы с хвостом на этом корпусе |
| Padding счётчиков | счётчики локальны для воркера, общих горячих записей нет |
| Быстрый путь для `^.{111}` | в Go это счёт рун, а не длина в байтах; выигрыш ~0.4 мкс на запрос |

## Отвергнуто

| Что | Почему |
|---|---|
| Свой regex-движок | другой масштаб задачи |
| Литералы из 2–3 обычных байт | E6: поиск дороже regex, который они экономят |
| `madvise(SEQUENTIAL/WILLNEED)` | E8: эффекта нет |
| Индекс префиксов только по первому байту | заменён индексом по двум байтам; на время это не повлияло (E4), двухбайтовый оставлен: корзины короче |
