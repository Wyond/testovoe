# Подробности к README

То, что не поместилось в две страницы README. История решений — `DECISIONS.md`, все замеры — `EXPERIMENTS.md`.

## Как устроен сквозной поток

```
4 читателя, каждый — свой файл (порции по 1 МБ) → границы элементов массива → ограниченная очередь → N воркеров:
    simdjson (NEON) → нормализация → предфильтр → regex → результат без id
→ писатель: id = (элементов в предыдущих файлах) + № в файле
```

1. **Чтение** (`stream_reader.go`).
   - Файлы читаются как партиции: 4 читателя берут их по очереди, внутри файла порядок сохраняется.
   - Читатель не уходит дальше чем на 16 файлов от первого недочитанного.
2. **Границы сообщений** (`splitter.go`).
   - Каждый файл — один JSON-массив в строку, не JSONL.
   - Сканер ищет конец каждого объекта: учитывает только строки (с `\`) и глубину вложенности, внутри строк прыгает через `bytes.IndexByte`.
   - Сам элемент проверяет парсер. Повреждённый JSON — всегда ошибка, а не пустой запрос.
3. **Очередь** (`stream_queue.go`).
   - Ограничена числом чанков и байтами (256 МБ), при заполнении читатель ждёт.
   - Буфер чанка принадлежит читателю до передачи в очередь, потом воркеру до `release`.
   - Буферы ходят по ограниченным спискам свободных; выросшие под огромный элемент не сохраняются.
4. **Разбор и нормализация** (`parser_simdjson.go`, `normalize.go`).
   - Запрос нормализуется так: `METHOD URL HTTP/1.1`, заголовки в исходном порядке и регистре, тело целиком, без percent-декодирования.
   - simdjson через тонкий слой на C++ пишет нормализованный запрос прямо в буфер воркера.
   - Если simdjson отказывает, элемент разбирает jx, а причина отказа считается. На корпусе отказов 0.
   - Нормализация есть в трёх реализациях: jx, `encoding/json` (контрольная) и simdjson. Все три сверяются побайтно с подготовленным корпусом.
5. **Писатель** (`stream_writer.go`).
   - Назначает `id`, когда известно число элементов во всех предыдущих файлах. Поэтому `id` те же, что у одного читателя и у matcher-only.
   - Повтор `id` — ошибка, и в конце проверяется, что записан каждый `id`.

## Предфильтр и движки

- **Предфильтр** (`filter_analyze.go`, `filter_build.go`, `filter_scan.go`).
  - Инвариант: если регулярка совпадает, правило — кандидат.
  - Условия выводятся из синтаксического дерева того самого выражения, которое скомпилировано:
    - литеральный префикс — индекс по двум первым байтам;
    - обязательный литерал — 3-граммы в блочном фильтре Блума на 16 КБ, проход с шагом 2;
    - ограничения на длину;
    - допустимые первый и последний байт.
  - Под `(?i)` буквы `k` и `s` в литерал не попадают: в Unicode с ними совпадают символ Кельвина и длинная S.
  - Итог: 11 735 правил за префиксом, 391 за литералом, 46 проверяются всегда; 13.65 вызова regex на запрос.
- **Движки.**
  - Движок для правила выбран калибровкой по времени (`config/backends.json`): 11 352 правила — Go, 6 — RE2, 7 — Rust regex.
  - Правило уходит с Go, только если другой движок быстрее как минимум на 20% и ни разу не ответил иначе.
  - 807 правил, которые Go не компилирует, исполняет PCRE2.

## Что означает результат

Правила nmap описывают ответы серверов на свои пробы. К HTTP-запросам применимы только самые общие из них, поэтому в выводе всего 6 сервисов из 1 250:

| сервис | правило (проба) | что на самом деле совпадает | запросов |
|---|---|---|---:|
| `ventrilo` | `^.{111}` (UDP Ventrilo) | любой запрос от 111 символов | 1 114 159 |
| `mongodb` | `^.*version.....([\.\d]+)` (TCP mongodb) | заголовок Chrome `sec-ch-ua-full-version: "127.0…"` | 284 583 |
| `pc-duo`, `pc-duo-gw` | `^.........(.*)\0` (UDP) | NUL-байт после 9-го символа | 13 055 |
| `dominoconsole` | `^([^/]+)/([\w._-]+):([^:]*):([^:]*):` | текст вида `a/b:c:d:` от начала запроса | 1 082 |
| `landesk-rc` | `^(?!HTTP\|RTSP\|SIP).{264}$` (NULL) | ровно 264 символа | 611 |

- **У 816 001 запроса (73%) единственное совпадение — `ventrilo`.**
- **Протокол пробы (TCP/UDP), порты и `rarity` не учитываются:** по ТЗ каждый запрос проверяется всеми правилами.
- **Приоритет — наша модель.** Имена дедуплицируются внутри списков `hard` и `soft` и располагаются в порядке правил исходного файла. nmap выбирает пробы по `rarity` и портам, а после softmatch сервиса S смотрит только hard-правила того же S. Поэтому первый элемент `hard` — не «вердикт nmap».

## Сверка с nmap (E25)

- **Эталон.** Каждое правило скомпилировано PCRE2 в байтовом режиме, как у nmap, и прогнано по всем 1 114 166 запросам без предфильтра: `matcher oracle`, отчёт в `results/oracle.log`.
- **Расхождение одно:** `landesk-rc` `.{264}$` на 33 запросах (0.003%). Это запросы длиной 265 байт с `\n` в конце: в PCRE `$` совпадает и перед финальным `\n`, у нас — только в конце текста.
- **Разница «символ против байта» не проявилась ни разу.** Невалидного UTF-8 в корпусе нет, не-ASCII байты есть в 2% запросов.
- **Лимит перебора у эталона.** На 351 огромном запросе эталон упирается в лимит на правилах вида `^.*X`. Там его ответ неизвестен, такие пары не сравниваются.

## Память

- **Очередь ограничена 256 МБ, но элемент массива должен лежать в памяти целиком.** Самый большой запрос (загрузка zip, сотни МБ в JSON) потребовал буфер 536 МБ.
- **Пиковый RSS — 1.8–2.8 ГБ.**
- **Go-аллокаций 0.03 на запрос, но эта цифра описывает только Go-кучу:**
  - simdjson за прогон наращивает свои буферы на ~1.2 ГБ, они считаются отдельно;
  - PCRE2 выделяет `match_data` на каждый вызов;
  - RE2 и Rust держат собственные кэши.
