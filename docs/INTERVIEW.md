# Материал к разбору

Основано на коде в этом репозитории. Цифры — из `docs/EXPERIMENTS.md` и `results/summary.md`; обоснования решений — в `docs/DECISIONS.md`. «Сделано» здесь значит: есть в коде и чем-то проверено.

Разделы идут в порядке работы. Где позднее решение изменило раннее, это сказано прямо в тексте. Текущая конфигурация и итоговые числа — README и E27.

## История за две минуты

1. Задача — много regex против одного входа, а не WAF и не nmap. Правила описывают ответы серверов, применяем их к запросам как готовую нагрузку.
2. Сначала сквозной naive: парсер правил → конвертер JSON в бинарный корпус → все скомпилированные regex на каждый запрос → JSONL. Он же эталон.
3. Ускорение — не быстрее исполнять regex, а реже их вызывать. Из AST каждого паттерна выводится необходимое условие; не выполнено — regex не запускается. Не выведено — паттерн проверяется всегда.
4. Подтверждает тот же движок, поэтому результат fast обязан совпасть с naive построчно. Это и есть проверка.
5. Сначала JSON был вынесен в отдельную фазу: matcher работал по mmap и индексу, воркеры брали диапазоны ID с общего атомарного счётчика. Сейчас это режим matcher-only.
6. Профиль дважды показал не то, что я ожидал: сначала три регистронезависимых паттерна съедали почти всё regex-время, потом короткие литералы оказались дороже regex, который они экономили.
7. Потом основным стал сквозной поток: каждый прогон заново разбирает JSON (simdjson), 4 читателя читают файлы как партиции.
8. 807 правил, которые Go не компилирует, вернул через PCRE2. Для каждого правила движок выбран калибровкой.
9. Сверил вывод с байтовой семантикой nmap на всём корпусе: расходятся 33 запроса, причина — `$`.

## Вопросы и ответы

**Что именно фильтруется?**
Пары запрос×паттерн. Запрос не пропадает: строка результата есть для каждого, в том числе пустая.

**Почему фильтр корректен?**
Каждое условие — следствие из дерева того самого выражения, которое скомпилировано. Concat: достаточно требования одного потомка. Alternate: объединение по веткам, ветка без требования отменяет условие. Необязательные части ничего не требуют. Практически: синтетический набор, где каждое правило хотя бы раз срабатывает, плюс построчное сравнение с naive на реальных запросах. Это отсутствие найденных расхождений, а не доказательство.

**Почему байтовый поиск корректен, если Go работает по рунам?**
Go декодирует вход как UTF-8. Руна литерала может совпасть только со своей канонической кодировкой, значит эти байты стоят во входе подряд. Исключение — U+FFFD: он совпадает с любым невалидным байтом, такие литералы не используются.

**Что с `(?i)`?**
Go сворачивает по Unicode: `k` совпадает с U+212A, `s` — с U+017F. Я беру только отрезки литерала из ASCII-рун, у которых вся орбита в ASCII, то есть без `k` и `s`. Для них сравнение без учёта ASCII-регистра точное. Тест перебирает все 128 рун.

**Чем Go отличается от PCRE здесь?**
Двумя вещами. Во-первых, 807 паттернов Go не компилирует: lookaround, атомарные группы, possessive, backreference. В основной конфигурации их исполняет PCRE2. Во-вторых, остальные компилируются, но значат не совсем то же: `.` считает символы, а не байты, `\xff` — это U+00FF, `$` — только конец текста. Сверка с байтовым PCRE2 на всём корпусе (E25) нашла одно расхождение: 33 запроса из-за `$`. Разница «символ против байта» на этих данных не проявилась: невалидного UTF-8 в корпусе нет.

**Почему не Aho–Corasick?**
Сначала сделал `bytes.Contains` на каждый литерал, как и планировалось, — профиль показал больше половины времени там. Вместо библиотеки написал однопроходный фильтр на 3-граммах, около 60 строк. Aho–Corasick в этом проекте не измерял, так что сравнения с ним нет.

**Почему регистр/короткие литералы важнее алгоритма поиска?**
Потому что стоимость определяют несколько паттернов. Три `(?si)^.*<address>Apache/` давали 204 из 229 мкс regex-времени на запрос. Пока для них не было условия, остальной фильтр ничего не значил.

**Что такое «эквивалентное подтверждение»?**
`(?s)^.*X` совпадает ровно тогда, когда `X` совпадает где-нибудь. Fast подтверждает через `X`, naive — оригиналом. Это замена Go-выражения на Go-выражение, и diff её проверяет.

**mmap экономит память?**
Нет. Он убирает корпус из Go-кучи, но прочитанные страницы всё равно в RSS и в page cache. `pread` в буфер воркера дал то же время.

**Где узкое место?**
- **Matcher-only.** После предфильтра в однопоточном профиле больше всего времени приписано первому обращению к байтам запроса (E7–E9). Это гипотеза: счётчиков кэша на macOS нет.
- **Поток на 10 воркерах (E27).** Чтение с поиском границ занимает 0.93 с из 2.98 с, то есть узкое место не оно. Работа воркеров дорожает с их числом: 12.5 с у одного воркера против 20.5 с в сумме у десяти; 6 ядер из 10 энергоэффективные. Ещё ~31% времени воркеры простаивают, причину не мерил.

**Почему порядок файла, а не rarity?**
Это наш детерминированный порядок. `rarity` управляет тем, какие probe отправлять; у нас probe не отправляются.

**Что именно выдаётся на запрос?**
Два отдельных списка, `hard` (сработавшие `match`) и `soft` (сработавшие `softmatch`). Внутри списка имя сервиса встречается один раз, на месте первого сработавшего правила этого сервиса в порядке строк файла. Сервис может быть в обоих списках. Выбор проб и итоговый вердикт nmap не воспроизводятся, поэтому первый элемент `hard` — не «что выбрал бы nmap». «Приоритет probe» из ТЗ я трактую как порядок правил в файле и говорю об этом прямо.

**Почему батч 256?**
Стартовое значение. Измерил 16…4096 — разницы за пределами шума нет.

**Что на 1B?**
Индекс 8 ГБ только на смещения, корпус в терабайтах, прогон на часы. Нужны сегменты, шарды со своим курсором, checkpoint с непрерывным watermark, идемпотентный вывод. Claim — это не commit.

## JSON без аллокаций — опыт с OpenTelemetry

Идея packed buffers (`Bytes{Buf, Pos}`) использована дважды:
- корпус на диске — это `Buf` (`corpus.bin`) и `Pos` (`corpus.idx`);
- в конвертере запросы файла лежат в одном буфере с массивом концов.

JSON сначала разбирался `encoding/json`: 74 аллокации на запрос. После замены на `jx` — 18.8. Конвертация стала 10.2 с вместо 14.2, CPU вдвое меньше, корпус побайтно тот же (E14).

Вариант с `DecodeBytes` даёт ноль аллокаций, но не быстрее. Оставшееся время — раскодирование `\uXXXX` в больших телах и последовательная запись на диск, а не GC.

Неожиданно выяснилось, что до замены декодера узким местом было окно конвейера: один файл на 700 МБ останавливал остальных.

## Аллокации и тяжёлый хвост

- **Аллокации.** Fast-режим на чистом Go в установившемся состоянии — 0 аллокаций на запрос, это показывает `-benchmem`. Всё изменяемое (биты кандидатов, буфер вывода, штампы) создаётся один раз на воркер. С нативными движками это описывает только Go-кучу: PCRE2 выделяет `match_data` на вызов, а simdjson, RE2 и Rust держат свои буферы.
- **Хвост.** Время растёт с байтами. Запросы больше 1 МБ — это 0.03% штук, но 22% байт и 15% времени. Один запрос на 108 МБ держит воркер около 0.2 с. Батчи по 256 ID это не убирают; на этом корпусе хвост мал относительно 1.5 с, которые тогда шёл весь прогон (E15).

## Откуда запросы по 100 МБ

Это загрузки файлов в облака (pCloud, OneDrive, TikTok, Box, Google Drive), причём раздутые самим датасетом. JSON-строка не может хранить произвольные байты, поэтому каждый байт файла, невалидный для UTF-8, записан как `�` — 3 байта вместо одного. У запросов от 1 МБ это 67% байт; в корпусе они в 1.78 раза больше своего `Content-Length`. 0.03% запросов дают 22% байт корпуса.

Вывод для продакшена: о таких запросах решаем до чтения тела по `Content-Length` и `Content-Type`. Проверяем заголовки, начало тела и заголовки частей `multipart`, а файлы — отдельной очередью или асинхронно (E17).

## Почему не RE2 / Rust regex, хотя в статьях они в разы быстрее

Проверил C++ RE2 через `go-re2` (cgo) за тем же предфильтром (E18).
- **Без предфильтра** RE2 действительно в 2.5 раза быстрее Go: 11 365 вызовов на запрос.
- **С предфильтром** полный прогон медленнее на 35–60%: остаётся ~13 вызовов на запрос. На мелких запросах RE2 не хуже Go, на средних его тормозит отключённая для RE2 замена `^.*X`, на больших бинарных телах он в 5–6 раз медленнее. Почему на больших телах — не установил: профиль Go видит только `runtime.cgocall`, внутрь C-кода не смотрит.

Главный рычаг — предфильтр, а не движок: он убрал ровно ту работу, где RE2 сильнее. Статья мерила 5 выражений на 100 МБ, у нас режим обратный.

Попутно нашлась тонкость семантики: в RE2 `.` не совпадает с невалидным байтом UTF-8, в Go совпадает. Из-за этого одна наша эквивалентная замена выражений для RE2 давала лишние совпадения; тест поймал, замена теперь зависит от движка.

## Гибрид движков и PCRE2 для исключённых правил

- **Выбор по измерению, а не по виду.** `calibrate` меряет каждое правило на Go, RE2 и Rust на отдельной выборке и переносит правило, только если выигрыш устойчивый и ответы не расходятся. Ушло 13 правил из 11 365, полный прогон стал на ~30% быстрее, результаты те же.
- **Семантика как условие корректности.** Предфильтр выведен из того, как правило читает Go. Поэтому Rust и PCRE2 получают выражение в распечатке Go, где классы записаны явно: в Rust `\d` по умолчанию Unicode, в PCRE `\s` включает `\v`.
- **807 исключённых правил.** PCRE2 возвращает их все: 611 запросов получают новые совпадения, время +3–15%. Предфильтр для них строится по ослабленной форме (без lookaround), язык которой шире исходного.
- **Ошибка в PCRE2.** Рандомизированный тест нашёл, что JIT PCRE2 10.49 читает за концом входа, оканчивающегося невалидным UTF-8. Для WAF это вопрос безопасности. Сначала JIT был выключен совсем; теперь он работает только на валидном UTF-8, а невалидный вход идёт в интерпретатор (E21). Срабатывания лимитов исполнения считаются отдельно, а не как «нет совпадения». В итоговом прогоне их 0 в основной конфигурации и 16 в наивном проходе.

## Потоковый режим и SIMD-парсер

- **Почему поток.** Основной замер теперь каждый раз читает исходный JSON: файл → границы элементов → ограниченная очередь → воркеры (разбор, нормализация, предфильтр, regex, вывод). Бинарный корпус оставлен как matcher-only, отдельной строкой.
- **Выбор парсера проверял, а не брал из описания:**
  - `simdjson-go` на arm64 просто не работает (`SupportedCPU() == false`);
  - `sonic` имеет NEON, но его backend не проверить;
  - simdjson (C++) печатает активную реализацию — у нас `arm64 (ARM NEON)` — и счётчики показывают, что он разобрал все 1 114 166 сообщений без единого отказа.
- **Сколько дал.** Сквозным путём быстрее jx в 1.36 раза на 1 воркере и в 1.53 раза на 10 (E27), при побайтно тех же нормализованных данных и тех же результатах.
- **Что я сначала сказал неправильно.** Что выигрыш съедает cgo и что он бывает только на больших телах. Замер показал: пустой cgo-вызов — 15 нс, около 2%, а на обычных сообщениях simdjson тоже быстрее на 12–15%. Первый замер был на нагретой машине.
- **Пределы.**
  - На нагруженной машине с одним читателем поток упирался в чтение и поиск границ; на спокойной это узкое место уже не главное (E27).
- **Параллельные читатели (E24, D21).**
  - **Схема.** Файл здесь как партиция в Kafka: K читателей берут файлы по очереди, внутри файла порядок сохраняется, элемент адресуется парой (файл, № в файле). Глобальный `id` считает писатель — база файла плюс номер, — как только известны счётчики всех предыдущих файлов. `id` совпадают с однопоточными, вывод сверен с matcher-only.
  - **Эффект.** На спокойной машине 3.17 → 2.99 с на 10 воркерах (1.06×). Первая серия на нагруженной машине показала 1.18×; я перемерил и поправил вывод (E27). Чтение при 4 читателях занимает 0.93 с из 2.98 с, то есть уже не узкое место. Теперь время уходит на дорожающую работу воркеров (6 ядер из 10 энергоэффективные) и ~31% простоя, причину которого не мерил.
  - **Для 1B** следующий шаг — сделать ключом сам адрес (файл, №), чтобы каждый файл отчитывался о прогрессе независимо, как партиция со своим offset.
  - Огромный элемент массива приходится держать целиком.
  - «0 аллокаций» — про Go-кучу: буферы C++ simdjson выросли на 1.2 ГБ, и Go их не видит.

## Сверка с nmap

- **Как проверял.** Каждое правило скомпилировал PCRE2 в байтовом режиме, как это делает nmap, и прогнал без предфильтра по всем 1.1 млн запросов (E25).
- **Что нашлось.** Одно расхождение: `landesk-rc` `.{264}$` на 33 запросах. У PCRE `$` совпадает и перед финальным `\n`, у нас — только в конце текста.
- **Чего не нашлось.** Разницы «символ против байта» на этих данных нет: невалидного UTF-8 в корпусе нет. Механизм при этом реальный, на него есть тест.
- **Что считаю важным.** Эталон сам упирается в лимит перебора на огромных запросах. Такие пары я вынес отдельно, а не записал в расхождения.

## Независимое ревью

После реализации код проверял отдельный агент с задачей сломать инвариант фильтра (E12). Ложных отрицаний он не нашёл, но нашёл пять дефектов на границах: переполнение 16-битной таблицы корзин, обнуление 32-битного штампа, запросы больше 1 ГиБ, зависание `prepare -workers 0`, `headers`-массив. Ни один не проявлялся на текущих данных; все исправлены и закрыты тестами. Его дифференциальные тесты в репозиторий не вошли — это отчёт, а не воспроизводимая часть проекта.

- Разбор грамматики файла и терминов nmap.

## Где AI мешал или ошибался

- В этой сессии: профиль с инлайнингом приписал время не той строке, и я потратил шаг на двухбайтовый индекс префиксов, который ничего не изменил (E4). Причину показал отдельный замер по паттернам.
- В этой сессии: добавил 2-байтовые литералы как «бесплатное» условие — они оказались дороже regex (E6), пришлось сузить правило.
- В этой сессии: тестовые правила с `|` внутри regex при разделителе `|` — парсер их справедливо отверг.
- До этого (по handoff): уверенность в цифрах с четырёх запросов, неверный редьюсер вердикта, «unsupported не срабатывают», обещания про L1.

## Что решал сам (пользователь)

Go; бинарный корпус и курсор; полный набор TCP+UDP; требование независимой критики; запись решений и экспериментов; запрет переносить старые цифры. Дефолты D1–D8 взяты из рекомендаций handoff и отдельно не подтверждались — это стоит проговорить на разборе.

## Чего нет и о чём сказать прямо

- С nmap расходятся 33 запроса из-за `$`. Исправить можно, но это меняет вывод, поэтому оставлено как известное ограничение.
- Выбор проб и вердикт nmap не воспроизводятся: выдаются полные списки в порядке правил файла.
- Нет формального доказательства фильтра.
- Замеры на одном ноутбуке с ядрами двух типов; линейность по ядрам на однородной машине не проверялась. На Linux проверены сборка и корректность, но не скорость.
- Aho–Corasick, Hyperscan, regexp2 не измерялись.
