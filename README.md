# waap-matcher

Матчинг 1 114 166 HTTP-запросов против всех 12 172 правил `nmap-service-probes` на Go. Для каждого запроса — список сервисов, раздельно `match` и `softmatch`, в порядке приоритета. История решений и все замеры — `docs/DECISIONS.md`, `docs/EXPERIMENTS.md`, `docs/INTERVIEW.md`.

Apple M4 (4 производительных + 6 энергоэффективных ядер), 24 ГБ, Go 1.27.2. Медианы трёх прогонов с паузой 20 с перед каждым; результат пишется в файл. Сырые данные — `results/run.log`, `results/metrics.jsonl`; потоковые числа с 4 читателями — `results/readers.log`.

## 1. Сквозной потоковый режим (основной)

Каждый прогон заново читает 699 JSON-файлов (7.3 ГБ) и проходит весь путь до записи результата:

```
4 читателя, каждый — свой файл (порции по 1 МБ) → границы элементов массива → ограниченная очередь → N воркеров:
    simdjson (NEON) → нормализация → предфильтр → regex → результат без id
→ писатель: id = (элементов в предыдущих файлах) + № в файле
```

| воркеров | с | req/s | JSON МБ/с | speedup |
|---:|---:|---:|---:|---:|
| 1 | 15.38 | 72 447 | 477 | 1.00× |
| 2 | 8.24 | 135 149 | 890 | 1.87× |
| 4 | 4.54 | 245 573 | 1 618 | 3.39× |
| 8 | 3.45 | 323 040 | 2 128 | 4.46× |
| 10 | 3.53 | 315 807 | 2 080 | 4.36× |

**Параллельные читатели** (10 воркеров, по 3 прогона по кругу): 1 читатель — 4.07 с, 2 — 3.61 с, 3 — 3.49 с, 4 — 3.46 с. На одном воркере число читателей не влияет (15.71 и 15.70 с).

**Парсеры при одинаковом матчере** (поочерёдно, по 3 прогона): simdjson против контрольного jx.

| воркеров | jx | simdjson | ускорение |
|---:|---:|---:|---:|
| 1 | 20.31 с | 15.38 с | 1.32× |
| 10 | 4.78 с | 3.47 с (321 тыс. req/s) | 1.38× |

- **Backend проверен в работе:** `simdjson 4.6.4, arm64 (ARM NEON)`. Все 1 114 166 сообщений разобрал simdjson, переходов на jx — 0. jx никогда не запускается раньше simdjson: он получает только отказы, и они считаются вместе с причиной.
- **Корректность:** нормализованные байты обоих парсеров совпали с подготовленным корпусом на всех запросах. Вывод потока совпал с matcher-only при 1 и 10 воркерах, с 1 и 4 читателями. Повреждённый JSON (16 вариантов в тестах) — всегда ошибка, а не пустой запрос.
- **Память:** пиковый RSS 1.8–2.5 ГБ; Go-аллокаций 0.03 на запрос. Ограничения этой цифры — в разделе «Где упёрся».

## 2. Matcher-only (стоимость JSON исключена)

Те же запросы один раз подготовлены в бинарный корпус (`corpus.bin` + индекс, 10.8 с), дальше читаются через mmap.

| воркеров | с | req/s | speedup |
|---:|---:|---:|---:|
| 1 | 4.94 | 225 772 | 1.00× |
| 10 | 0.95 | **1 177 771** | 5.22× |

**Baseline:** наивный однопоточный проход всех 12 172 правил тем же движкам на 100 000 запросах — 173.0 с (578 req/s). Быстрый режим на тех же запросах — 0.53 с, **в 327 раз быстрее**; выводы побайтно совпали.

## Как получить числа

```bash
brew install re2 pcre2 simdjson pkg-config rust   # один раз
scripts/run.sh                                     # основной режим: simdjson; данные скачаются в data/
```

- **Свои пути к данным:** `LEGIT=/path/Legitimate MAL=/path/Malicious scripts/run.sh`.
- **Если simdjson не установлен,** скрипт останавливается с ошибкой, а не меряет тихо что-то другое.
- **Контрольный вариант на jx:** `PARSER=jx scripts/run.sh`.
- **Быстрая проверка (~3 мин):** `QUICK=1`.
- **Время полного прогона:** ~23 мин до серии читателей, она добавляет 16 коротких прогонов.
- **Кэш baseline:** наивный проход переиспользуется, пока не изменились код, правила, движки или корпус.
- **Один потоковый прогон:** `bin/matcher stream -parser simdjson -backends results/backends.json -excluded pcre2 -workers 10 -readers 4 <Legitimate> <Malicious>`; `READERS=1` — один читатель.

## Как устроено

1. **Чтение.** Файлы — как партиции: 4 читателя берут их по очереди, внутри файла порядок сохраняется. Глобальный `id` считает писатель, когда известно число элементов во всех предыдущих файлах, — он тот же, что у одного читателя и у matcher-only.
2. **Границы сообщений.** Каждый файл — один JSON-массив в строку, не JSONL. Сканер ищет конец каждого объекта: учитывает только строки (с `\`) и глубину вложенности, внутри строк прыгает через `bytes.IndexByte`. Сам элемент проверяет парсер.
3. **Очередь.** Ограничена числом чанков и байтами (256 МБ), при заполнении читатель ждёт. Буферы ходят по ограниченным спискам свободных; выросшие под огромный элемент не сохраняются.
4. **Нормализация.** `METHOD URL HTTP/1.1`, заголовки в исходном порядке и регистре, тело целиком, без percent-декодирования. simdjson через тонкий слой на C++ пишет нормализованный запрос прямо в буфер воркера.
5. **Предфильтр.** Из синтаксического дерева каждого правила выводится условие, без которого совпадения нет: префикс, обязательный литерал, длина, первый и последний байт. Остаётся **13.65 вызова regex на запрос вместо 12 172**.
6. **Подтверждение.** Движок для каждого правила выбран калибровкой по времени: 11 352 — Go, 6 — RE2, 7 — Rust regex. 807 правил, которые Go не компилирует, — PCRE2.

## Несовместимые паттерны

- **Учёт.** Go не компилирует 807 правил: lookahead/lookbehind 685, атомарные группы 79, possessive 26, обратные ссылки 16, повтор >1000 — 1.
- **Возврат через PCRE2.** Для предфильтра правило ослабляется: lookaround выбрасываются, обратная ссылка становится `.*`. Язык ослабленной формы шире исходного, поэтому фильтр совпадений не теряет. Перебор ограничен лимитами, их срабатывание считается отдельно.
- **JIT PCRE2.** Используется только на валидном UTF-8: в PCRE2 10.49 JIT читает за концом входа, оканчивающегося невалидным байтом (нашёл тест).
- **Семантика и сверка с nmap.** Наши движки работают по символам UTF-8 и понимают `$` как конец текста. nmap работает по байтам, и у него `$` совпадает и перед финальным `\n`. Эталон — каждое правило, скомпилированное PCRE2 в байтовом режиме, — прогнан по всем 1 114 166 запросам без предфильтра (`matcher oracle`, `results/oracle.log`):
  - **расхождение одно:** `landesk-rc` `.{264}$` на 33 запросах (0.003%) длиной 265 байт с `\n` в конце, то есть из-за `$`;
  - **«символ против байта» не проявилось ни разу:** невалидного UTF-8 в корпусе нет, не-ASCII байты есть в 2% запросов, но ни одно правило на них не разошлось;
  - **на 351 огромном запросе эталон упирается в лимит перебора** на правилах вида `^.*X`. Там его ответ неизвестен, и такие пары не сравниваются; у нас на них 5 совпадений `mongodb`.

## Что означает результат

- **Совпадения — по форме запроса, а не по содержанию.** Правила nmap описывают ответы серверов на свои пробы. К HTTP-запросам применимы только самые общие из них, поэтому в выводе всего 6 сервисов из 1 250:

  | сервис | правило (проба) | что на самом деле совпадает | запросов |
  |---|---|---|---:|
  | `ventrilo` | `^.{111}` (UDP Ventrilo) | любой запрос от 111 символов | 1 114 159 |
  | `mongodb` | `^.*version.....([\.\d]+)` (TCP mongodb) | заголовок Chrome `sec-ch-ua-full-version: "127.0…"` | 284 583 |
  | `pc-duo`, `pc-duo-gw` | `^.........(.*)\0` (UDP) | NUL-байт после 9-го символа | 13 055 |
  | `dominoconsole` | `^([^/]+)/([\w._-]+):([^:]*):([^:]*):` | текст вида `a/b:c:d:` от начала запроса | 1 082 |
  | `landesk-rc` | `^(?!HTTP\|RTSP\|SIP).{264}$` (NULL) | ровно 264 символа | 611 |

  У 816 001 запроса (73%) единственное совпадение — `ventrilo`.
- **Учитывается ли протокол пробы.** Нет: по ТЗ каждый запрос проверяется всеми ~12 тыс. правил. Протокол (TCP/UDP), порты и `rarity` проб не учитываются. Фильтр по ним — другая постановка задачи, её надо согласовать.
- **Приоритет — это наша модель, а не алгоритм nmap.** Сервисы идут в порядке проб в файле, внутри пробы — в порядке строк. Сам nmap выбирает пробы по `rarity` и портам, а после softmatch сервиса S смотрит только hard-правила того же S. Поэтому первый элемент `hard` — не «вердикт nmap».

## Что пробовал и что отбросил

- **SIMD-парсер JSON.**
  - `minio/simdjson-go` на arm64 не работает: вне amd64 `SupportedCPU()` возвращает `false`.
  - `bytedance/sonic` имеет NEON-сборку для arm64, но активный backend во время работы не проверить, а поля он отдаёт как Go-строки.
  - Выбран simdjson (C++): сообщает активную реализацию и разбирает поля по порядку без дерева.
- **Где выигрывает simdjson.** На отдельных сообщениях: на обычных он быстрее jx на 12–15%, на крупных телах из `\uXXXX` — в ~1.9 раза. Пустой cgo-вызов стоит ~15 нс, около 2% разбора сообщения, — и пакетный вызов всех сообщений сразу дал ту же скорость.
- **Конвертация в бинарный корпус как основной путь** — 10.8 с только на подготовку. Поток проходит весь путь за 3.3–3.7 с и не пишет промежуточные 5.4 ГБ.
- **Регулярки:**
  - RE2 или Rust regex целиком вместо Go — не быстрее, отсюда гибрид по калибровке;
  - литералы из 2–3 обычных байт — поиск дороже regex;
  - `pread` вместо mmap — то же время.

## Где упёрся

- **Поток на 10 воркерах по-прежнему упирается в чтение.** С одним читателем чтение и поиск границ (`-split-only`) занимали 3.06 с из 4.07 с. С 4 читателями — 2.31 с из 3.46 с, а суммарное время `read` выросло с 2.4 до 6.6 с: параллельные чтения из page cache мешают друг другу. Чем именно ограничены, не мерил. После 3 читателей выигрыша почти нет, воркеры простаивают ~30% времени.
- **Память ограничена, кроме одного случая.** Файл читается порциями по 1 МБ, очередь — до 256 МБ. Но элемент массива должен лежать в памяти целиком: самый большой запрос (загрузка zip, сотни МБ в JSON) потребовал буфер 536 МБ.
- **«0.02 аллокации на запрос» — только Go-куча.** Аллокации C/C++ она не видит:
  - simdjson за прогон нарастил свои буферы на ~1.2 ГБ — это считается отдельно;
  - PCRE2 выделяет `match_data` на каждый вызов;
  - RE2 и Rust держат собственные кэши.

  Go-аллокаций за прогон 7–8 ГБ в байтах; по профилю аллокаций они в основном приходятся на буферы под элементы больше 1 МБ, а не на повседневную работу.
- **Matcher-only.** Профиль приписывает основное время первому обращению к байтам запроса. Счётчиков кэша на macOS нет — это гипотеза, не вывод.
- **Машина.** MacBook Air без вентилятора: одна и та же конфигурация в разных сериях отличалась до 15% (поток на 10 воркерах с 4 читателями — от 3.21 до 3.71 с).

## 100M / 1B

- **Адрес вместо глобального `id`.** Параллельное чтение файлов уже есть (`id` = база файла + № в файле). Дальше ключом должен стать сам адрес (файл, №): тогда каждый файл, как партиция со своим offset, отчитывается о прогрессе независимо и писателю не нужно ждать предыдущие.
- **Сбои.** Счётчик захвата — не подтверждение. Нужен checkpoint с watermark (конец непрерывно обработанного префикса) и идемпотентный вывод.
- **Несколько машин.** Шард — файлы или сегменты со своим курсором и watermark, балансировка по байтам, а не по числу запросов.
- **Огромные элементы** лучше разбирать потоково или отдавать отдельной очереди с лимитом, а не держать целиком.
- **Вывод.** `ventrilo` совпадает почти со всеми запросами — на 1B такие правила надо агрегировать.
