# waap-matcher

Матчинг 1 114 166 HTTP-запросов против правил `nmap-service-probes` на Go. Подробности: `docs/DECISIONS.md` (что и почему), `docs/EXPERIMENTS.md` (что измерено), `docs/INTERVIEW.md`.

## Как получить числа

```bash
scripts/run.sh
```

Скрипт скачивает данные в `data/`, если их нет, собирает бинарь, гоняет тесты, конвертирует JSON в бинарный корпус, сверяет naive с fast и печатает таблицу. Результат — `results/summary.md`, сырые метрики — `results/metrics.jsonl`. Занимает около 5 минут, из них 3.5 — naive baseline. Нужно ~6 ГБ RAM и 5.4 ГБ на диске под корпус.

- Корпус уже распакован: `LEGIT=/path/Legitimate MAL=/path/Malicious scripts/run.sh`
- Свои точки и повторы: `WORKERS="1 2 4 8" REPEATS=3 BASELINE=100000 scripts/run.sh`
- Один прогон: `bin/matcher run -mode fast -workers 8 -out results/out.jsonl` (есть `-cpuprofile`)

Полный путь из пустой папки проверен: `git clone` → `scripts/run.sh` скачал, распаковал и прогнал всё, корпус побайтно совпал с локальным. Скачивание `legitimate.zip` (1.1 ГБ) с сервера openappsec заняло около часа на ~320 КБ/с. Файл правил закреплён на коммите nmap `3b71f80` (SHA256 `bd1bc6b1…`): в `master` он уже изменился.

## Результаты

Apple M4 (4 производительных + 6 энергоэффективных ядер), 24 ГБ, Go 1.27.2, тёплый page cache. Медиана из трёх прогонов; время включает форматирование и запись JSONL (без `fsync`).

- **Фазы:** конвертация JSON → бинарный корпус 10.2 с (однократно, медиана из трёх), инициализация правил 0.14 с, matching на 10 воркерах 1.54 с. Подряд — 11.9 с.
- **Baseline:** naive, один воркер, 100 000 запросов с равным шагом по корпусу — 202.7 с, 493 req/s. Те же запросы через предфильтр на одном воркере — 0.77 с (медиана из трёх), в 264 раза быстрее.
- **Sanity:** результаты naive и fast на этих 100 000 запросов побайтно одинаковы; 1 воркер и 10 воркеров на всём корпусе дают одинаковые строки, без пропусков и повторов.
- **Аллокации:** fast-режим — 0 на запрос (`go test ./internal/matcher -bench Match -benchmem`); конвертация на `jx` — 18.8 на запрос.
- **Хвост:** p50 запроса 2 КБ, p99 20 КБ, максимум 108 МБ. 0.03% запросов больше 1 МБ дают 22% байт и 15% времени (`bin/matcher stats`).
- **Большие запросы — загрузки файлов, раздутые датасетом.** 351 запрос от 1 МБ — загрузки в pCloud, OneDrive, TikTok, Box, Google Drive. При записи в JSON каждый невалидный для UTF-8 байт файла заменён на `�` (3 байта): 67% их байт — этот символ, в корпусе они в 1.78 раза больше своего `Content-Length` (самый большой: 59.5 МБ zip → 108 МБ). Исходные байты не восстановить, бинарные сигнатуры по таким телам бессмысленны.
- **Линейности после двух ядер нет.** На 4 ядрах 72%, на 10 — 51%. Однотипных ядер всего 4, поэтому вклад медленных ядер и общих ресурсов этим замером не разделить; спад на 3–4 ядрах медленными ядрами не объясняется, причина не найдена.

Вывод — `results/out.jsonl`, по строке на запрос, включая пустые: `{"id":4,"hard":["pc-duo","ventrilo"],"soft":[]}`. Имена идут в порядке приоритета (порядок Probe в файле, затем строк), `match` и `softmatch` отдельно. Совпадения есть у 1 114 159 запросов: `ventrilo` (`^.{111}`) у всех, `mongodb` у 284 583; ни одного softmatch.

## Как устроено

1. **Подготовка.** JSON → `corpus.bin` (запросы подряд) + `corpus.idx` (смещения `uint64`) + `manifest.json`. Нормализация: `METHOD SP URL SP HTTP/1.1 CRLF`, заголовки в порядке и регистре JSON, пустая строка, тело целиком; без percent-decoding.
2. **Правила.** Каждая строка `match`/`softmatch` компилируется стандартным `regexp` без переписывания.
3. **Предфильтр.** Из AST каждого паттерна выводится необходимое условие; пока оно не выполнено, regex не вызывается:
   - 10 941 паттерн — литеральный префикс от начала текста (индекс по двум байтам);
   - 379 — обязательный литерал внутри (один проход по запросу, Bloom-фильтр по 3-граммам);
   - 45 — условие не выведено, проверяются всегда;
   - дополнительно: границы длины, допустимые первый и последний байт.
   После фильтра остаётся 13.4 вызова regex на запрос вместо 11 365.
4. **Воркеры.** Общий атомарный счётчик раздаёт диапазоны по 256 ID; запросы читаются из mmap, всё изменяемое локально.

## Что пробовал и что отбросил

- **`bytes.Contains` на каждый литерал** (276 проходов по запросу) — занимал больше половины времени; заменён одним проходом.
- **Литералы из 2–3 обычных байт** (`"19"`, `":0"`) — поиск оказался дороже regex, который они экономили: 88% профиля. Короткие литералы теперь только с управляющего байта.
- **Регистронезависимые литералы** сначала не извлекались, и три паттерна `(?si)^.*<address>Apache/` давали 204 из 229 мкс regex-времени на запрос. После добавления условия — ускорение в 8 раз.
- **`encoding/json` в конвертере заменён на `jx`:** строки раскодируются в переиспользуемые буферы. Аллокаций в 4 раза меньше, CPU вдвое меньше, конвертация 14.2 → 10.2 с, корпус побайтно тот же (`scripts/bench_decoders.sh`). Вариант с файлом целиком в памяти даёт ноль аллокаций на запрос, но не быстрее.
- **Окно конвертера «N файлов вперёд»** заменено лимитом байт: из-за него файлы по 700 МБ разбирались по очереди.
- **`pread` батча вместо mmap, `madvise`** — время то же.
- **Размер батча 16…4096** — разницы за пределами шума нет.
- **C++ RE2 (`wasilibs/go-re2`, cgo) вместо Go `regexp`** за тем же предфильтром (сборка с `-tags re2_cgo`): результаты на корпусе те же, но полный прогон на 35–60% медленнее. Без предфильтра RE2 в 2.5 раза быстрее Go, однако после предфильтра остаётся ~13 коротких вызовов на запрос, и выгоду съедает цена вызова и большие тела. Попутно выяснилось, что в RE2 `.` не берёт невалидный UTF-8, поэтому одна из наших замен выражений для него неэквивалентна; она отключается в зависимости от движка. Оставлен Go `regexp`.
- **Гибрид движков по калибровке** (`matcher calibrate` → `-backends`): движок каждому правилу выбирается по измеренному времени. 13 правил из 11 365 ушли на RE2 или Rust regex — и полный прогон стал на ~30% быстрее (1.45 с против 1.85 с на 10 ядрах в одном замере), результаты те же. Rust regex целиком — вровень с Go, RE2 и PCRE2 целиком — медленнее. Требует cgo-зависимостей, поэтому не по умолчанию.
- **PCRE2 для 807 исключённых правил** (`-excluded pcre2`): возвращает все 807, 611 запросов получают новые совпадения, время +3–15%. Предфильтр строится по ослабленной форме правила (lookaround выброшены — язык только шире). JIT выключен: в PCRE2 10.49 он читает за концом входа, оканчивающегося невалидным UTF-8 (найдено тестом).
- **Aho–Corasick, Hyperscan, regexp2** — не пробовал.

## Где упёрся

После предфильтра однопоточный профиль приписывает основную часть времени первому обращению к байтам запроса, а не regex и не фильтру. Диск при этом не читается, а замена mmap на `pread` показывает ~2.8 с копирования из 7.3 с профиля и то же общее время. То есть заметную долю прогона занимает доставка 5.4 ГБ из page cache; почему она идёт на ~2 ГБ/с, я не выяснил. Счётчиков `perf` на macOS нет, поэтому «memory bandwidth» остаётся гипотезой.

Полный прогон от JSON ограничен конвертацией: 10.2 с против 1.54 с matching. Она грузит ~1.3 ядра из 10: самый большой файл (734 МБ, тела из `\uXXXX`) разбирается 2.3 с одним потоком, а запись 5.4 ГБ на диск идёт строго по порядку (~3.3 с).

Машина — MacBook Air без вентилятора. Под долгой нагрузкой одна и та же конвертация однажды заняла 41 с вместо 14. Прогон после часа простоя (из чистой папки, E16) дал 6.74 с на одном воркере и 1.19 с на десяти: эффективность 88% на 4 ядрах и 57% на 10 против 72% и 51% в таблице выше. Похоже, значительная часть «нелинейности» — нагрев, но это не проверено отдельно.

## Несовместимые паттерны

- **807 из 12 172 (6.6%) не компилируются** в Go и исключены: negative lookahead 670, атомарные группы 79, possessive-квантификаторы 26, обратные ссылки 16, lookahead 13, lookbehind 2, повтор >1000 — 1. Отчёт печатается при каждом запуске. Сколько совпадений из-за этого потеряно, не измерялось.
- **Остальные 11 365 компилируются, но Go — не PCRE:** `.` и классы считают руны, а не байты; `\xff` — это U+00FF; `$` — только конец текста; `(?i)` сворачивает по Unicode. Сверки с PCRE не было, совместимость не заявляется. Naive и fast используют один движок, поэтому их совпадение говорит только о корректности фильтра.

## 100M / 1B

Без изменений не масштабируется:

- **Индекс и корпус.** 1B запросов — 8 ГБ только смещений и терабайты данных. mmap-файл перестаёт помещаться в page cache, прогон упирается в диск. Нужны сегменты с собственными индексами.
- **Конвертация.** Уже сейчас в 6–7 раз дольше matching; на 100M — десятки минут. Её надо распараллеливать по сегментам или читать исходный формат без JSON.
- **Длительность и сбои.** Счётчик `Add` — это захват диапазона, а не подтверждение. Нужен checkpoint с watermark (конец непрерывно завершённого префикса) и идемпотентный вывод: после сбоя диапазоны за watermark обработаются повторно.
- **Несколько машин.** Шард = часть корпуса со своим курсором и своим watermark; балансировать по байтам, а не по числу запросов; владение шардом требует координации.
- **Вывод.** `ventrilo` совпадает почти со всеми запросами — такие правила на 1B придётся агрегировать, иначе запись результатов станет узким местом.
